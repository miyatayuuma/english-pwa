# P3.5 音声研究・引き継ぎ

## 暫定選定

**事前生成は Kokoro-82M v1.0 ONNX q8 を第一候補とする。** CPUだけで生成でき、20人に別々のプリセットを割り当てられ、出力前の発音補正が可能。採用は発音・自然さ・人物の識別を実際に聴いて判断する。BobとJenniferの比較で声の好みが分かれる場合は、Supertonic 3の追加プリセットを比較する。

リアルタイムは同じKokoro音声を使えるPixel端末内を先に測る。WASM/q8で測定経路を使える状態にした。PCのブラウザでは実時間より遅かったため、次回の端末側評価はAndroidネイティブを優先し、同じ課題でWASMとの速度差を確認する。会話の表情に十分な差が出ない場合、録音素材を使わずに設計できるQwen3-TTS VoiceDesignを、GPU環境で短い対照試験にかける。

## 実測と発音

AMD EPYC 9V74、Linux x86_64、CPU割当9、ORT 1.32.0、推論スレッド4、キャッシュ取得後の実行。2モデルを同じホスト上で並行して測った初回パイロット。中央値とp95は各30クリップの合成時間で、後処理を含まない。RTFは合成秒 / トリム前音声秒で、小さい方が速い。トリム前の余白量がモデルで異なるため、レイテンシも併記する。

| 実測 | Kokoro | Supertonic |
| --- | ---: | ---: |
| ロード対象（2声込み） | 93.41 MB | 398.95 MB |
| CPU合成 30クリップ | 27.13秒 | 34.56秒 |
| 中央値 / p95 | 0.985 / 2.281秒 | 1.052 / 2.980秒 |
| 合成のみの集計RTF | 0.362 | 0.387 |
| FFmpeg等の後処理 30クリップ | 3.16秒 | 2.87秒 |
| プロセスの最大RSS | 424.0 MiB | 512.9 MiB |

Kokoro全員の追加初回生成は63クリップで合成46.78秒・後処理5.52秒。20声込みの参照アセットは約102.81 MB。後続の発音指定2本は個別の再生成で、`kokoro-cast-measurements.json` はこの直近の差分生成の記録。GPU・VRAM・Pixel実値はここから推定しない。

- Kokoroが自動生成した音素列で、`record` と `present` はそれぞれ動詞・名詞の強勢を区別した。`dyed` と `died` は同じ音素列だった。
- 自動の `I read it yesterday, but I'll read it again tomorrow.` は `read` が2箇所とも /riːd/ だった。完成ページには /rɛd/ と /riːd/ を明示したKokoro音声も置いた。音素列の検査は、実際に聞こえる音声の品質評価を代替しない。
- `flatter`、`flatly`、`former`、`yield` は独立した短語として収録した。同音異綴語の認識表記を正誤判定に使わない。Supertonicとブラウザの発音成功率、自然さ、20人の識別率は試聴前の未確定項目。
- 公開版の人物データと肖像を使い、試聴文は新規作成。全128 MP3を FFprobe で検査し、FFmpeg でデコード。24 kHz、モノラル、合計266.712秒、2,163,904 bytes。

画面はデスクトップ Chromium と、Pixel相当の画面幅・操作条件のChromiumで確認した。20人のカード、モデル切替、MP3の進行、3ターンの会話、オフラインの配布HTML再生を検証した。ブラウザ標準の実音色はOSのエンジンに依存するため試聴端末の確認対象。

## 事前生成の設計

- 1クリップを教材ID、話者ID、表示英文のSHA-256、音声プロフィールのバージョンで特定する。キャッシュキーにはモデルID・重みのリビジョン、声ID、アクセント、話速、発音指定ハッシュ（指定時）、エンコード仕様も含める。本番ではフロントエンドや辞書・依存更新も同じ生成レシピの版に含める。教材IDが固定でも英文や発音が変わったら差分生成する。
- 波形を10 ms RMSフレームで検出し、呼吸音や語末を残す余白を付ける。音声区間のRMSを-20 dBFSへ寄せ、ピークを-1.5 dBFS以下に収める。同梱のMP3は64 kbpsモノラル。製品ではMP3を互換性基準とし、Opus 24–32 kbpsとの聴取・ブラウザ互換を比較する。差し替え時は弱い語頭・語末の切れを確認する。
- 生成途中のファイルは一時名に書き、成功したファイルと音源ハッシュを記録する。途中停止後は同じコマンドで差分再開できる。数万件ではジョブを不変マニフェストのキーで分割し、ワーカーごとの出力を一本の発行マニフェストに集約する。現スクリプトはモデルごとに単一ライターを前提とし、同一出力ディレクトリへの並行実行は避ける。
- 規模試算（CPU実測からの外挿）。3秒/本、Kokoro RTF 0.36と後処理0.10秒/本で、1ワーカーは約1.18秒/本。3,000本 約59分、10,000本 約3.3時間、30,000本 約9.8時間。短文の起動オーバーヘッド、I/O、同時ワーカー数により変動。最初に実教材100本で測る。
- 容量試算（3秒/本、コンテナ等のオーバーヘッドを除く）。MP3 64 kbpsは3,000 / 10,000 / 30,000本で約72 / 240 / 720 MB。Opus 24 kbpsは約27 / 90 / 270 MB。GPU効率とVRAMは未測定。GPUを試すなら、ロード後の同一100本をCPU 4スレッドと比較し、同精度・同出力長・同エンコード条件でピークVRAMと総時間を計る。ONNX q8 CPUとFP32 GPUでは発音・韻律差も再確認する。

## リアルタイム

### Pixel 9

Googleの[端末仕様](https://support.google.com/pixelphone/answer/7158570)では Tensor G4 / RAM 12 GB。以下のモデル容量・ブラウザ対応は資料またはファイル実寸であり、Pixelの実測ではない。

- 試聴室の測定はKokoro WASM/q8を基準とする。q8モデルは92.36 MB、1声は0.52 MB。別途JS・音素化辞書・ONNX Runtime WASMを取得する。WebGPUはfp32モデル約326 MBとランタイムを要する。試験用SDKとモデルを固定した。
- 初回初期化と、モデル常駐のまま生成するラウンドを分ける。各ラウンドで同じ短文を2回、長文を1回生成して合成時間、WAV完成時間、RTF、音声長をJSONに保存する。初回ロードには外部取得があり、生成処理は端末内。Python版とブラウザ版は同じ声IDを使うが、フロントエンドの音素化とONNXランタイム版が違うため、発音境界と同一人物として聞こえるかを確認する。ここでの「WAV完成」は全発話生成後で、ストリーミングの初音声時刻ではない。HTMLのキャッシュ保持とページ再読込後のオフライン復帰は端末上で個別に確認する。
- PC上のHeadless Chromium 140、WASM/q8、クロスオリジン分離なしで生成からJSON保存まで確認。初回準備19.06秒、短文7.00 / 6.35秒、長文17.02秒、RTF 2.230–2.456。最初の短文は声ファイル取得も含みうる。通信を切った常駐時も3回とも生成できた（RTF 2.339–2.393）。端末上のリアルタイム性はAndroidネイティブを含め別に測る。[初回の実測JSON](desktop-chromium-wasm-measurement.json) / [オフライン再測定JSON](desktop-chromium-wasm-offline-measurement.json)
- 次の比較はAndroid API + sherpa-onnxの [Kokoro](https://github.com/k2-fsa/sherpa-onnx/releases/tag/tts-models) と [Supertonic 3](https://k2-fsa.github.io/sherpa/onnx/tts/supertonic.html)。量子化・音素化・声対応は配布モデルごとに確認する。端末実験では冷間起動、常駐時、ASR稼働時、10分連続の4条件を含め、PSS、電力・温度、ASRの確定結果と反応時間を記録する。Androidでは `adb shell dumpsys meminfo <package>`、`adb shell dumpsys thermalservice`、`adb shell dumpsys batterystats` を使用できる。
- 将来の会話では同じ音声IDを全機能で使い、文章境界で先読み・キャンセル可能にする。音声再生中は誤認識や自己入力を防ぐための聞き返し・割り込み制御を実測で決める。合成が遅い場合は固定の導入文を事前生成し、次の短文単位をバックグラウンドで合成する。

### クラウド候補と無料枠

クラウド試験の第一候補は、無料プランの上限で提供元が停止する [Cloudflare Workers AI / Deepgram Aura-2](https://developers.cloudflare.com/workers-ai/models/aura-2-en/)。英語の固定プリセットは20以上ある。公式[料金](https://developers.cloudflare.com/workers-ai/platform/pricing/)の 10,000 neurons/日と Aura-2 の 2,727.27 neurons/1,000文字から、このモデル単独なら約3,666文字/日、30日で約11万文字。上限はUTC 0時にリセットされ、固定の月間無料枠はない。実運用の上限は 8,000 neurons/日を初期案とし、同じアカウントでLLM等を使うなら残量を共有して差し引く。Freeプランを維持し、超過エラーは既存音声に戻す。WorkerのAIバインディングを使えばブラウザにAPIキーを渡さず、speakerを固定できる。実測と契約適用の確認は未実施。モデルページはデータ保持なしと記載し、[出力の権利は提携先条項](https://deepgram.com/terms)を含め運用時に確認する。Kokoroとは声が変わるため、採用には事前生成と会話で同じ経路を使うか、代替音声を別途選ぶ判断が必要。

#### Chirp 3 HD

[公式料金](https://cloud.google.com/text-to-speech/pricing)の100万文字/月のうち、試験設計では専用請求アカウントの全Chirp利用を専用バックエンドに集約し、利用者/日上限と月80万文字の停止閾値を設ける。リクエスト前に、空白を含む送信単位・再試行をトランザクションで予約し、残量不足・計測不能・月境界の照合不明時は呼び出しを停止する。複数入口または既存利用と料金無料枠を共有する場合は集約が済むまで利用を開始しない。Cloud Monitoringと請求エクスポートで照合する。[Cloud Billing予算](https://docs.cloud.google.com/docs/get-started/learn-about-billing)は通知であり、停止はアプリ側で行う。

認証はサーバーのサービスアカウント・ADCを使用し、クライアントにキーを置かない。キャラクターとGoogle voice nameをサーバー側で固定。メッセージの保持は必要最小限にし、可能な再生はローカル音源をキャッシュする。初回音声チャンクまで、全音声、p50/p95、失敗率、キャッシュヒット率を測る。Chirpは[同時ストリーミング枠とリクエスト枠](https://docs.cloud.google.com/text-to-speech/quotas)にも従う。閾値・請求・API可用性が検証できる前は端末内または既存音声を使う。
